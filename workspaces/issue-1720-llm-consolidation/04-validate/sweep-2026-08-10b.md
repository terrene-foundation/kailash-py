## 5. Decision points — judgment calls, NOT self-decided

### Decision A — `#1997` vendor key redaction: which fix shape?

The issue frames a binary; there is a third option it did not consider.

- **Option 1 — lower the contiguous-run threshold 40→32 for `[A-Za-z0-9]`.**
  Pro: claims Mistral immediately, one line. Con: widens over-redaction across every error body —
  trace IDs, request IDs and un-hyphenated UUIDs are all 32-char runs, so it directly worsens the
  open over-redaction finding on the exact surface `body_snippet` exists to provide.
- **Option 2 — context-anchored rule** (redact a 32-char run only near `mistral`/`api_key`/
  `authorization`). Pro: preserves diagnosability. Con: misses the case the module's own comment
  calls out — a secret bare in a raw exception string with no nearby keyword.
- **Option 3 (RECOMMENDED) — split by whether the vendor has a prefix.** Groq (`gsk_`) and xAI
  (`xai-`) have anchorable prefixes: fix those two now, precisely, with zero over-redaction cost —
  the same shape already used for `hf_`/`fw_`. That leaves only Mistral and Cohere genuinely
  facing the Option 1/2 trade-off, on a much smaller surface.
  Pro: closes half the gap at no cost and shrinks the hard decision. Con: two commits instead of
  one, and Mistral/Cohere still need a call afterwards.

**Recommend Option 3.** It is the only one that does not pay the over-redaction cost for vendors
that never needed it.

### Decision B — `#2022`: where should provider resolution live?

`kailash-ml` needs a provider resolver; kaizen's canonical fail-closed `detect_provider` is
PRIVATE (`kaizen.nodes._env_model`; `hasattr(kaizen.nodes,"detect_provider")` is `False` —
verified). Options: (a) publish a public kaizen resolver and have ml depend on it; (b) have ml
resolve independently, duplicating the mapping and the drift risk; (c) have `BaseAgentConfig`
resolve internally when omitted, fail-closed.

**Recommend (a).** The `#1952` work already made provider resolution a kaizen-owned contract;
(b) guarantees drift, and (c) hides the resolution from the caller. Con of (a): it adds a public
API surface kaizen must then keep stable.

### Decision C — `#2023`: per-step or blanket?

**Recommend per-step, which is why it is filed rather than fixed.** None of the eight remaining
sites currently exercises the affected path, so a blanket editable-install would lengthen every
job and pull heavy optional deps for no present benefit. Con of per-step: it is 8 judgment calls
instead of one sweep, and it stays open longer.

### Decision D — CodeQL alert `#11400`

Advisory (`required_status_checks.contexts` is `[]`). The single net-new HIGH is a **verified
false positive**: the tainted value is `_password_column`, a column NAME set by
`.password_column("password_hash")`, flowing into a 4-hex-char log-correlation fingerprint.

- **Dismiss as `false_positive`.** Pro: stops a known-false HIGH polluting every future PR's
  baseline — which is exactly what produced session L's unverified "no security severity" claim.
  Con: dismissal is repo-wide and permanent, so if the code later evolves such that a genuine
  secret reaches `_identifier_fingerprint`, the dismissal suppresses a then-true finding. Needs
  `security_events: write` (permission status UNKNOWN — not attempted).
- **Do nothing.** Pro: zero risk. Con: the false HIGH stays on main's baseline.

**Recommend dismissal with the written justification**, on the condition that the acceptance
criteria note the re-alert gap. Rewriting `_identifier_fingerprint` to placate the heuristic is
BLOCKED: its docstring records why SHA-256 over `hash()` (PYTHONHASHSEED randomisation breaks
cross-process log correlation), so "fixing" it reintroduces a real defect to silence a fake one.
