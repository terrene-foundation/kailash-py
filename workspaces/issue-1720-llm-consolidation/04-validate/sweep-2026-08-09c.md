  verification that had not run. Rounds 6, 7 and 8 EACH found a defect in the prior round's fix, so

### Decision B — where does `credential_scrub` live? **(gates ~1,944 sites)**

**Recommend: relocate to `kailash.utils`** — unchanged from session J, but the premise is CORRECTED
and the scope is SMALLER than stated there.

- Core DOES ship a scrubber: `kailash.utils.url_credentials.mask_error_text`, plain core, already on
  the import path. Session J's "src/kailash has NO scrubber" was false.
- **Measured, it masks TWO carriers and nothing else** — URL userinfo AND sensitive query params.
  A bare OpenAI key, bare JWT, Slack token, 32-char Mistral key and `Authorization: Basic` all pass
  through intact.
- **So the relocation is still needed for the vendor vocabulary — but less of the surface depends on
  it than session J implied.** Both lenses independently established that HIGH-1's two LOG sinks
  need **no scrubber at all**: the fix is the in-core `safe_exception_frames`, already imported by
  the file four lines above the leak.
- **Cons (real)** — moves a 1,200-line ReDoS-analysed module across a package boundary; couples
