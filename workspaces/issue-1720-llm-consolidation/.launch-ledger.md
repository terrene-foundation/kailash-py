## L4 landed: the finalizer guard was INERT, and hid a second deadlock

`except Exception: pass` in ten finalizers did **zero work** against the hazard that motivated it —
a deadlock is not an exception, so nothing is ever raised for the handler to catch. It bought no
safety and swallowed real release failures.

**The standard Rule 3 remedy is contraindicated here.** Adding a logging call to the except branch
takes the very lock whose re-entry IS the deadlock. The fix DELETES the cleanup call: no call, no
exception, no handler, no Rule 3 exposure. The stdlib C-level deallocators close sqlite3/socket
handles anyway, which a Python-level `close()` from a GC callback cannot do safely.

**Second deadlock, never documented in the issue, and deterministic (100% reproduction):** four
finalizers re-acquire a NON-REENTRANT `threading.Lock`. A finalizer fires at an arbitrary bytecode
boundary on whichever thread dropped the last reference — including a thread already inside one of
those locked sections, which then blocks on itself forever.

blind to a finalizer swallowing a differently-named cleanup call (`release()`, `shutdown()`,
`rollback()`), and five such sites exist. A shape-level guard test now walks EVERY `__del__` under
`src/kailash`, so a ninth site reds CI regardless of the method name.
